第四章：并行与服务架构 —— 大模型怎么切、怎么服务？

1. 为什么需要并行？

一个 70B FP16 模型需要 ~140GB 显存，而 A100 只有 80GB → 单卡放不下。

即使放得下（如 7B 模型），单卡的算力和带宽也有限 → 吞吐不够。

所以我们需要：

  • 模型并行：把一个大模型拆到多张卡上
  • 数据并行：多个副本服务不同请求（提升吞吐）

2. 模型并行

2.1 Tensor Parallelism（TP，张量并行）

核心思想：把一个大的矩阵乘法拆到多张卡上并行计算。

以 Y = XW 为例，W 是 [d, d] 的权重矩阵：

列切分（Column Parallel）
W = [W₁ | W₂] 按列切两半
卡 1Y₁ = X × W₁batch, d/2
卡 2Y₂ = X × W₂batch, d/2
合并Y = [Y₁ | Y₂]拼接，免通信
行切分（Row Parallel）
W = [W₁ / W₂] 按行切两半，X 也对应切开
卡 1Y₁ = X₁ × W₁batch, d
卡 2Y₂ = X₂ × W₂batch, d
合并Y = Y₁ + Y₂需 AllReduce

在 Transformer 层中的典型切法：

MLP 层：
  gate_proj / up_proj: Column Parallel（输出各算一半）
  down_proj: Row Parallel（输入各出一半，AllReduce 合并）

Attention 层：
  QKV proj: Column Parallel（每个 head 在不同卡上）
  o_proj: Row Parallel（AllReduce 合并）

QKV 按 head 列切分（免通信），o_proj 行切分（AllReduce 合并）

通信开销：每个 Transformer 层需要 2 次 AllReduce（Attention 后 + MLP 后），TP=2 时每次 AllReduce 传输 2×d×batch×seq_len 个元素。

⚠️ 关键约束：TP 的通信量与 hidden_dim × batch 成正比。TP 度数越大，通信开销越大。通常 TP≤8，且要求 GPU 之间有高速互联（NVLink）。

2.2 Pipeline Parallelism（PP，流水线并行）

核心思想：把模型按层切到不同卡上，像流水线一样处理。

层分配卡0 · L0-9卡1 · L10-19卡2 · L20-29卡3 · L30-39
请求 A卡0卡1卡2卡3
请求 B…卡0卡1卡2卡3
请求 C……卡0卡1卡2卡3
请求像流水一样依次经过各卡；卡间只传 hidden state（batch × seq × d_model）

问题：气泡（Bubble） —— 卡在等前一批数据时空闲

时间 →t0t1t2t3t4t5t6t7
卡 0ABC空ABC空
卡 1空ABC空ABC
卡 2空空ABC空AB
卡 3空空空ABC空A
虚线"空"格就是气泡：流水线填充和排空阶段，下游卡只能干等

减小气泡的方法：

  • Micro-batching：把一个 batch 拆成多个 micro-batch，交错执行
  • Interleaved 1F1B：更激进的调度，交替使用不同层的 chunk

PP 的通信：每层组之间只需发送 hidden state（大小 = batch × seq_len × d_model），远小于 TP 的 AllReduce。

💡 TP vs PP 怎么选？ - 优先用 TP（通信量大但延迟低，适合节点内 NVLink 互联） - 模型太大、单节点放不下时用 PP（跨节点通信，带宽低但通信量小） - 通常组合使用：节点内 TP，节点间 PP

2.3 Data Parallelism（DP，数据并行）

核心思想：模型不切，每个副本完整部署一份，把不同请求分发到不同副本。

            ┌── 副本1（GPU 0-1，TP=2）──► 请求 A、B
负载均衡 ──►├── 副本2（GPU 2-3，TP=2）──► 请求 C
            └── 副本3（GPU 4-5，TP=2）──► 请求 D、E

推理场景的 DP 是最"便宜"的并行：

  • 无通信：训练里 DP 每步要 AllReduce 同步梯度；推理没有反向传播，副本之间零通信，唯一需要的是请求级负载均衡
  • 线性扩展：N 个副本 ≈ N 倍吞吐

但 DP 有两个前提：

  1. 单副本能放下模型。放不下就先 TP/PP 凑出一个完整副本（一个副本占多张卡），再用 DP 复制——总 GPU 数 = DP × 每副本卡数
  2. 显存里除了权重还要留够 KV Cache 空间。副本数翻倍，集群的 KV Cache 总容量也翻倍——这才是 DP 提升并发能力的实际来源

💡 直觉：TP/PP 解决"能不能跑"，DP 解决"跑多快"。生产部署的标准公式 = 先用 TP 凑出能放下模型的最小副本，再用 DP 堆副本数提吞吐。

顺带一提：训练里的 FSDP / ZeRO-3（权重分片 + 用时聚合）在推理上等价于 TP，只是通信时机不同，推理框架一般直接用 TP，不单独讨论。

2.4 Sequence / Context Parallelism（SP / CP，序列并行）

动机：长上下文。seq_len 变长后，显存压力从权重转向激活和 KV Cache——这部分 TP 切不掉（或切不干净）。

SP（Sequence Parallelism，Megatron 式）：

TP 只切了 Linear 层，LayerNorm / residual 路径上的激活在每张卡上仍完整复制一份。SP 把这部分激活沿序列维度切开，每卡只存 seq_len/TP 的激活：

TP 区域内（Linear）:  按权重切，各算各的
TP 区域外（LayerNorm / residual）:  按序列切，每卡处理 seq 的一段
交界处的通信原语替换:
  AllReduce → AllGather + ReduceScatter（总通信量不变！）

SP 是 TP 的"省显存补丁"：通信量与纯 TP 相同，但消除了激活的重复存储。现代 TP 实现（Megatron、vLLM 的长序列场景）基本都内建 SP。

CP（Context Parallelism，Ring Attention）：

把整个序列（含 KV Cache）切成若干块分到多卡，每卡只保存自己那段的 Q/K/V：

CP=4，序列切成 4 段：
  卡0: 持有 Q₀,K₀,V₀  →  依次从环上收到 K/V₁,₂,₃  ─┐
  卡1: 持有 Q₁,K₁,V₁  →  依次从环上收到 K/V₂,₃,₀   │ 每收到一块 K/V，
  卡2: 持有 Q₂,K₂,V₂  →  ...                        │ 用 FlashAttention 的
  卡3: 持有 Q₃,K₃,V₃  →  ...                        │ 在线 softmax 增量更新
                                                   ─┘
  每卡 KV Cache 只占 1/4，通信（Ring P2P）与计算重叠

主要收益在超长上下文的 prefill（128K ~ 1M tokens）：单卡的 KV Cache 和注意力中间结果都放不下时，CP 几乎是唯一解。短序列不值得——Ring 通信步数随 CP 度线性增长。

⚠️ SP 和 CP 常被混为一谈：SP 切的是"TP 没覆盖到的激活"，依附于 TP 存在，随 TP 白送；CP 切的是"整个序列（含 KV Cache）"，是独立的并行维度，只有长上下文场景才需要。

2.5 Expert Parallelism（EP，专家并行）

动机：MoE 模型。DeepSeek-V3 总参数 671B、每 token 只激活 37B；Mixtral 8×7B 同理。MoE 层的 FFN 变成 E 个独立 expert，router 为每个 token 选 top-k 个。

核心思想：把不同 expert 放到不同卡上，token 按路由结果"快递"到对应卡计算，结果再送回来。

  token ─► router ─► top-2: expert 3, expert 7
                        │
      AllToAll dispatch（token 发往 expert 所在的卡）
                        │
        卡0: expert 0-3 计算    卡1: expert 4-7 计算
                        │
      AllToAll combine（结果发回原卡，按路由权重加权求和）

通信原语是 AllToAll，每个 MoE 层两次（dispatch + combine），对延迟敏感。

为什么 MoE 不用纯 TP？

  • 单个 expert 的 FFN 很小（几 GB 量级），TP 再切一刀收益小，每层 2 次 AllReduce 却照付
  • MoE 的价值在于计算稀疏性：每 token 只激活 top-k 个 expert。EP 让每卡只持有部分 expert、只算被路由到自己的 token，通信从稠密 AllReduce 变成"只传被路由 token"的 AllToAll
  • 671B 这种体量，EP 天然把权重摊到几十上百张卡（EP=64 时每卡只有 ~10GB 权重）

EP 的工程挑战：

  • 负载不均：router 的偏好让"热门 expert"所在卡过载 → DeepSeek 的 EPLB（Expert Parallel Load Balance）定期重排 expert 布局，并给热门 expert 加冗余副本
  • 小 batch decode 时 AllToAll 延迟占比高 → 大 EP 组需要 NVLink 域 + RDMA 配合
  • 现代主流做法：Attention 部分 TP/DP + MoE 部分 EP 的混合并行（DeepSeek 官方推理架构、SGLang/vLLM 的 wide-EP 部署均如此）；冷 expert 还可以 offload 到 CPU 内存按需加载

2.6 常见并行策略

六种并行方式对比（它们互相正交，可叠加）：

并行方式 切什么 通信原语 解决什么 典型约束
TP 权重矩阵 AllReduce ×2/层 单卡放不下、算力不够 需 NVLink，通常 ≤8
PP 层 P2P send/recv 跨机扩展 流水线气泡
DP 请求 / 副本 推理时无 吞吐 每副本须放全模型
SP 序列维度的激活 AllGather + ReduceScatter 长序列激活显存 依附 TP，通信量与 TP 相同
CP 整个序列（含 KV Cache） Ring P2P（可与计算重叠） 超长上下文 仅长上下文值得
EP MoE expert AllToAll ×2/MoE 层 MoE 权重巨大 负载均衡、延迟敏感

组合公式：总 GPU 数 = DP × TP × PP（长上下文再 ×CP，MoE 的 FFN 部分换成 EP）

例1: 70B dense，64 卡      → TP=8 × DP=8（8 个完整副本）
例2: 405B dense            → TP=8（节点内）× PP=16（跨节点）
例3: DeepSeek-V3           → Attention 用 DP/TP + MoE 用 EP=64，长上下文再叠 CP
例4: 1M token 上下文 prefill → TP=8 × CP=8

按模型和场景的快速选型：

模型大小 GPU 配置 推荐策略
7B 1×A100 单卡，无需并行
13B 1×A100 单卡 + 量化，或 TP=2
70B 4×A100 TP=4 或 TP=2+PP=2
70B 8×A100 TP=8 或 TP=4+PP=2
175B+ 16+ A100 TP=8 + PP=2+
MoE（如 DeepSeek-V3） 32+ 卡 Attention DP + MoE EP，配 EPLB
长上下文（128K+） 任意 在上述基础上叠 CP

3.2 调度器（Scheduler）—— 服务的核心大脑

调度器决定：每个 iteration 执行哪些请求、组成多大的 batch

关键决策：

  1. Prefill vs Decode 混合：一个 iteration 里同时做新请求的 prefill 和已有请求的 decode
  2. Chunked Prefill：把长 prompt 的 prefill 拆成多个 chunk，避免一个长 prefill 阻塞所有 decode
  3. 抢占（Preemption）：显存不够时，暂停某些请求，释放 KV Cache 给更高优先级的请求
Iteration N:
  Prefill chunk: 请求D 的前 256 tokens
  Decode: 请求A (token 47), 请求B (token 23), 请求C (token 81)

Iteration N+1:
  Prefill chunk: 请求D 的后 128 tokens（完成 prefill）
  Decode: 请求A (token 48), 请求B (token 24), 请求C (token 82), 请求D (token 1)

调度器的约束：
  新请求 prefill → 需要 KV Cache → 从 pool 分配
  如果 pool 不够 → 等待 / 抢占 / 拒绝

3.4 投机调度（Speculative Scheduling）

调度器还可以做更聪明的决策：

  • 预测下一个 iteration 会有多少新请求，提前预留显存
  • 预估每个请求的输出长度，优化 batch 组成
  • 对 SLO（Service Level Objective）敏感的请求给予优先级

4.3 分离式架构：Prefill-Decode Disaggregation

4.3.1 为什么要分离？

回想第一章的关键洞察：Prefill 是 compute-bound，Decode 是 memory-bound。它们对硬件的需求截然不同：

维度 Prefill 实例 Decode 实例
瓶颈 算力（FLOPS） 显存带宽（HBM BW）
理想 GPU H100（990 TFLOPS FP16） L40S（864 GB/s 带宽，算力适中）
batch 策略 小 batch 也能打满算力 大 batch 才能打满带宽
请求特征 短时、突发、计算密集 长时、稳定、访存密集

混部的问题：当 Prefill 和 Decode 共享同一组 GPU 时：

t0 – t5prefill A（长 prompt，吃满算力）decode Bdecode Cdecode D
↑ 同一 iteration 里 B/C/D 的 decode 全部被阻塞拖慢
t6+decode Adecode Bdecode Cdecode DA 加入，争抢带宽更激烈
结果：长 prefill 拖慢所有在途请求的 TPOT；decode 低算力需求浪费 FLOPS；prefill 与 decode 争抢同一份显存预算

分离后：

Prefill 实例专注 prefill：
  - 全力跑 prefill，GPU 利用率接近峰值算力
  - 不受 decode 干扰，TTFT 可预测

Decode 实例专注 decode：
  - 只做 decode，可以开大 batch 充分利用带宽
  - 不被 prefill 打断，TPOT 稳定
  - 可以用带宽/算力比更高的便宜卡

4.3.2 资源配比怎么算？

Prefill 实例和 Decode 实例的数量比不是拍脑袋的，核心公式：

设：
  T_prefill = 平均每个请求的 prefill 时间（在单个 Prefill 实例上）
  T_decode  = 平均每个请求的 decode 总时间 = avg_output_len × TPOT
  N_prefill = Prefill 实例数
  N_decode  = Decode 实例数

稳态条件：Prefill 吞吐 = Decode 吞吐

  N_prefill / T_prefill = N_decode / T_decode

→ N_prefill / N_decode = T_prefill / T_decode

举例：

场景：LLaMA-2-70B，avg_prompt=500 tokens，avg_output=200 tokens
  T_prefill ≈ 80ms（在 H100 上）
  TPOT ≈ 25ms（在 H100 上，batch=64）
  T_decode = 200 × 25ms = 5000ms

  N_prefill / N_decode = 80 / 5000 = 1:62.5

→ 1 个 Prefill 实例就需要 ~63 个 Decode 实例来消化！

这个比例看起来很夸张，但合理：

  • Decode 每个请求要跑几百步，而 prefill 只跑一次
  • 实际中 prefill 实例可以批量处理多个请求，比例会小一些

影响因素：

因素 Prefill 实例需求 ↑ Decode 实例需求 ↑
prompt 变长 ✅（计算量 ↑）
输出变长 ✅（decode 步数 ↑）
请求并发 ↑ ✅ ✅
模型变大 ✅ ✅
Decode batch ↑ ❌（单实例吞吐 ↑，总实例数 ↓）

💡 实战建议：先从混部开始，监控 prefill/decode 的时间比例。当 prefill 对 decode 的干扰显著影响 SLO 时，再考虑分离。分离后用自动扩缩容调整配比。

4.3.3 KV Cache 跨实例传输

Prefill 实例算完 KV Cache 后，需要传输给 Decode 实例。这是 PD 分离最核心的工程挑战。

KV Cache 有多大？

单层 KV Cache 大小 = 2 × seq_len × d_model × sizeof(dtype)

LLaMA-2-70B (d=8192, 80 层), prompt=500 tokens, FP16:
  = 2 × 500 × 8192 × 2 × 80
  = 1.31 GB

LLaMA-2-70B, prompt=4000 tokens, FP16:
  = 10.5 GB  ← 一个请求的 KV Cache 就 10GB！

传输方案对比：

方案 带宽 延迟 实现复杂度
TCP/RDMA over Converged Ethernet 25-100 Gbps 高 低
InfiniBand RDMA 200-400 Gbps 中 中
GPU Direct RDMA 200-400 Gbps 低 高

GPU Direct RDMA：KV Cache 直接从 Prefill GPU 的显存 → 网卡 → Decode GPU 的显存，不经 CPU 内存，减少两次拷贝和一次 CPU 参与。

普通 RDMAPrefill GPU 显存→CPU 内存→网卡→CPU 内存→Decode GPU 显存
2 次 GPU↔CPU 拷贝
GPU Direct RDMAPrefill GPU 显存→网卡→Decode GPU 显存
0 次 CPU 参与，延迟降低 40-60%

KV Cache 传输延迟的影响：

TTFT (分离式) = Prefill 计算时间 + KV Cache 传输延迟 + Decode 排队时间
TTFT (混部)   = Prefill 计算时间 + Decode 排队时间

多出来的就是 KV Cache 传输延迟。如果传输 1.3GB via IB RDMA (400 Gbps):
  1.3GB × 8 / 400Gbps ≈ 0.26ms  ← 很小，可接受

但 prompt=4000 tokens 的 10.5GB:
  10.5GB × 8 / 400Gbps ≈ 2.1ms  ← 仍然可控

⚠️ 关键：KV Cache 传输必须在 prefill 完成后、decode 开始前完成。如果传输延迟 > 一个 decode step 的间隔，就会在 decode 侧产生空转气泡。

4.3.4 Chunked Prefill + PD 分离

Chunked Prefill（本章 3.2 节介绍过）和 PD 分离是天然搭档：

不加 Chunked Prefill 的 PD 分离：Prefill 实例必须等完整 prompt 算完才能传 KV Cache，长 prompt 导致 Prefill 实例长时间被一个请求占住。

加 Chunked Prefill：把长 prompt 切成 chunk（如 512 tokens/chunk），算完一个 chunk 就传一部分 KV Cache 给 Decode 实例，Decode 可以更早开始生成：

切 chunk：传输与计算重叠，Decode 提前开工
Prefillchunk 1chunk 2chunk 3
KV 传输KV₁KV₂KV₃
Decode…开始 decode ↖ 收到 KV₁ 即可开工
不切 chunk：传 KV 是串行的尾巴
Prefill整个 prompt
KV 传输等待完整 KV
Decode…开始 decode

配合的关键收益：

  1. 降低 TTFT：Decode 不用等完整 KV Cache 传完就能开始（首 token 可在第一个 chunk 传完后立即生成）
  2. Prefill 实例更灵活：小 chunk 意味着更细粒度的调度，多个请求的 chunk 可以交错执行
  3. 传输分散：KV Cache 分批传输，避免瞬间大流量冲击网络

💡 注意：Chunked Prefill 下跨 chunk 的 attention 需要特殊处理（如 FlashAttention 的 incremental KV cache 更新），这在 vLLM 和 SGLang 中已有实现。

方案 核心思路 KV 传输方式 调度策略 特点
DistServe (2024) PD 完全分离，独立资源池 GPU Direct RDMA Prefill/Decode 独立调度 首个系统性的 PD 分离方案，证明了分离的 SLO 优势
Splitwise (2024) PD 分离 + chunked prefill IB RDMA 统一调度器协调两个池 微软方案，关注节点异构配比与成本优化
Mooncake (2024) PD 分离 + KV Cache 分离存储 GPU Direct RDMA + KV Pool 请求级调度 + KV Cache 预取 月之暗面方案，KV Cache 可缓存复用，支持 prefix caching
MemServe (2024) PD 分离 + 全局内存池 RDMA 内存感知调度 关注 KV Cache 的全局管理和复用

DistServe 的关键发现：

实验（LLaMA-2-70B, A100 GPU）：
  混部:  P99 TTFT = 8.2s, P99 TPOT = 120ms
  分离:  P99 TTFT = 1.5s, P99 TPOT = 28ms

  → 分离后 TTFT 降低 5.5×, TPOT 降低 4.3×
  → SLO 达成率从 30% 提升到 99%+

为什么差距这么大？因为混部下，一个长 prompt 的 prefill 就能让所有在途请求的 decode 延迟暴涨。分离后互不干扰。

Mooncake 的独特创新——KV Cache 复用：

传统 PD 分离:
  每次请求的 KV Cache 用完即弃

Mooncake:
  KV Cache 存入全局 Pool（CPU 内存 / SSD）
  → 如果新请求与旧请求有相同 prefix（如 system prompt）
  → 直接从 Pool 加载 prefix 的 KV Cache，跳过这部分的 prefill

  例：system prompt = 2000 tokens
  - 首次请求：正常 prefill，存入 Pool
  - 后续请求：加载 prefix KV Cache（~2ms from CPU），只需 prefill 用户输入部分
  → TTFT 降低 50-70%

4.3.6 什么场景下 PD 分离收益最大？

收益大的场景：

✅ 长 prompt（>1k tokens）
   → Prefill 耗时长，混部下对 decode 干扰大
   → 分离后 prefill 不阻塞 decode

✅ 高并发、输出长度差异大
   → 不同请求的 decode 时间差异大，混部调度困难
   → 分离后各自独立扩缩容

✅ 对 SLO 严格（如 P99 TPOT < 50ms）
   → 混部下长 prefill 导致 TPOT 尖刺
   → 分离后 TPOT 更稳定

✅ System prompt 复用（搭配 Mooncake 式 KV 缓存）
   → 大量请求共享 prefix，KV Cache 复用收益大

✅ 大规模集群（>16 GPU）
   → 集群够大才有资源做细粒度配比
   → 小集群分离反而增加调度开销

收益有限的场景：

❌ 短 prompt + 短输出（如聊天摘要）
   → Prefill 快、decode 也短，分离开销 > 收益

❌ 低并发场景
   → 混部本身没有资源争抢，分离无意义

❌ 小规模部署（<8 GPU）
   → 分离后每个池的 GPU 数太少，TP/PP 度数不够，反而更慢

❌ KV Cache 传输瓶颈（无高速网络）
   → 如果只有 TCP 网络，传输延迟可能抵消分离收益

决策流程：

  • 有高速互联（IB/RoCE）？
    • 是 → 高并发？>100 RPM？
      • 是 → 长 prompt（>500 tokens）？
        • 是 → PD 分离，收益大
        • 否 → 先试 chunked prefill
      • 否 → 混部够用，不必分离
    • 否 → 先升级网络

思考题

  1. TP=8 时，每个 Transformer 层需要几次 AllReduce？如果 batch 大，通信占比会怎样变化？
    参考答案

    次数与 TP 度无关：每层固定 2 次 AllReduce——Attention 的 o_proj（Row Parallel 输出合并）一次，MLP 的 down_proj 一次。TP=8 改变的是每次 AllReduce 的通信量和参与卡数（Ring AllReduce 的步数随 N 增长），不改变次数。

    batch 大时通信占比会上升。Decode 每步耗时 = 权重读取（固定，与 batch 无关）+ 计算（∝batch）+ 通信（∝batch）。小 batch 时权重读取占主导，通信被掩盖；batch 增大后权重读取被摊薄，通信在剩余时间里的占比越来越高，最终逼近由"计算速率 vs 互联带宽"决定的饱和值。这就是为什么 TP 必须限制在 NVLink 互联的单机之内，跨机要换 PP。

  2. PP 的气泡问题，micro-batching 是如何缓解的？能完全消除吗？
    参考答案

    把一个大 batch 拆成 m 个 micro-batch，让各 stage 流水起来：stage 2 处理 micro-batch 1 的同时，stage 1 处理 micro-batch 2，空闲时间被填满。气泡占比 ≈ (p-1)/(m+p-1)（p = stage 数），m 越大气泡越小。

    不能完全消除：① 流水的填充（warmup）和排空（drain）阶段天然存在——第一个 micro-batch 到达最后一个 stage 之前，后面的 stage 必然空闲；② m 也不能无限大：micro-batch 太小，每次前向的 kernel launch、权重读取等固定开销占比上升（decode 是 memory-bound，权重读取次数 = micro-batch 数，拆得越细读权重越频繁），通信轮次也增多。实践上 m 取 4-8，再配合 1F1B / interleaved 调度压缩显存和气泡。

  3. 分离式架构中，KV Cache 传输的延迟怎么影响 TTFT 和 TPOT？
    参考答案

    TTFT 直接增加：Decode 实例拿到 KV Cache 之前无法开始生成，传输延迟（几十到几百 ms，取决于 KV 大小和链路）完整加在 TTFT 上。缓解办法是流水化传输——按层或按 chunk 边算边传（chunked prefill 算完一块传一块），Decode 实例收到第一批 KV 即可开工，传输被 prefill 计算掩盖。

    TPOT 稳态下不受影响：传输是每个请求一次性的事件，不在逐 token 的生成循环里。但有间接影响——多请求同时迁移 KV 时，如果传输与数据面共享网络，带宽争抢会给 TPOT 引入抖动（p99 变差）。所以生产部署用独立的 RDMA/IB 链路传 KV（Mooncake 的核心设计之一就是把 KV 传输放到专用高速网络上）。

  4. 如果一个 70B 模型的平均 prompt 长度是 1000 tokens，平均输出 300 tokens，Prefill 实例吞吐 20 req/s，Decode 实例 TPOT=20ms，需要多少 Decode 实例才能跟上 1 个 Prefill 实例？
    参考答案

    套本章 4.3.2 的稳态公式 N_prefill / N_decode = T_prefill / T_decode：

    T_decode = 300 × 20ms = 6s，即一个请求要占 Decode 实例 6 秒 → 单 Decode 实例吞吐 = 1/6 req/s。N_decode = 20 ÷ (1/6) = 120 个。

    120:1 看似夸张，但这正是"decode 重、prefill 轻"的直接体现（与本章 1:62.5 的例子同构）。注意这个结果隐含 Decode 实例 batch=1；实际会开 continuous batching——batch=64 且 TPOT 仍 ≈20ms 时，单实例同时服务 64 个请求，吞吐 64/6 ≈ 10.7 req/s，只需 ~2 个 Decode 实例。配比对 batch 容量假设极其敏感，这是实战中配比调整的关键变量。

  5. Mooncake 的 KV Cache 复用在什么场景下收益最大？什么场景下几乎没有收益？
    参考答案

    收益最大：存在长公共前缀且 prefill 占比高的场景——多轮对话（历史轮次 KV 直接复用，不再重新 prefill）、共享 system prompt / few-shot 前缀的请求、RAG 命中相同检索文档、Agent 场景反复携带的长工具描述。本质是"省掉重复的 prefill 计算"，前缀越长、复用率越高，省得越多。

    几乎没收益：① 单轮、短 prompt、内容互不相同的流量（没有可复用的前缀）；② decode 主导的长生成场景（prefill 占比本来就小，省了不影响整体）；③ 复用成本高于重算的场景——KV 存在远端/CPU 内存，加载时间超过本地重算 prefill 的时间时，复用反而更慢（这也是 Mooncake 要把 KV 池架在高速互联上的原因）。

  6. DeepSeek-V3（671B 总参数、每 token 只激活 37B 的 MoE）做在线服务，为什么主流部署选 EP 而不是纯 TP？EP 最大的工程挑战是什么？
    参考答案

    选 EP 的根本原因是 MoE 的计算稀疏性与 TP 的稠密假设冲突：

    ① 单个 expert 的 FFN 只有几 GB，TP 把它再切一刀收益很小，但每层 2 次 AllReduce 的通信税照付——切得越碎，通信/计算比越难看。

    ② 更本质的：每个 token 只激活 top-k 个 expert。纯 TP 下所有 expert 的权重都参与计算（或至少都参与通信），稀疏性完全浪费；EP 让每卡只持有 E/EP 个 expert，token 经 AllToAll 只流向被路由的 expert，通信量与实际计算量都正比于"激活的部分"而非"总参数"。

    ③ 671B 的体量用 TP 摊需要极多组（TP=8 每组仍要 84GB+），EP=64 时每卡只有 ~10GB expert 权重，还能和 Attention 部分的 DP/TP 正交组合。

    最大工程挑战是负载不均：router 的偏好会让少数热门 expert 所在卡过载，整组进度被最慢的卡拖住（AllToAll 是同步原语）。解法是 DeepSeek 的 EPLB——定期统计路由分布、重排 expert 物理布局，并给热门 expert 加冗余副本。其次是 decode 小 batch 时 AllToAll 延迟占比高，需要大 NVLink 域 + RDMA 兜底。
