第二章：KV Cache 与内存优化 —— 显存都去哪了？

1. 朴素推理的问题：重复计算

没有 KV Cache 时，生成第 k 个 token 需要对前 k-1 个 token 全部重新做 attention：

生成 token 1: Attention(prompt)           → O(L)
生成 token 2: Attention(prompt + t1)      → O(L+1)
生成 token 3: Attention(prompt + t1 + t2) → O(L+2)
...
生成 token N: Attention(prompt + t1+...+tN-1) → O(L+N-1)

总计算量 = O(L + (L+1) + ... + (L+N-1)) = O(N·L + N²/2)

每个新 token 都要对所有之前的 token 重算 Q·K^T 和 softmax·V，这是巨大的浪费。

2. KV Cache 原理

2.1 核心思想

Attention 公式：

Attention(Q, K, V) = softmax(QK^T / √d) · V
  • Q 是当前 token 的 query 向量（只跟当前步有关）
  • K 和 V 是所有历史 token 的 key/value 向量

既然 K 和 V 来自前面的 token，且已经算过了，直接缓存起来就好！

生成 token 1: 计算 K₁,V₁，缓存。用 Q₁ 做注意力。
生成 token 2: 计算 K₂,V₂，拼入缓存。用 Q₂ 对 [K₁,K₂] 做注意力。
生成 token 3: 计算 K₃,V₃，拼入缓存。用 Q₃ 对 [K₁,K₂,K₃] 做注意力。
...

每步只需:
  1. 计算当前 token 的 Q, K, V（O(d²) 矩阵乘）
  2. 把新 K, V 追加到缓存
  3. 用当前 Q 对整个 KV 缓存做 attention（O(L·d)）

总计算量从 O(N²) 降到 O(N·L) —— 线性！

2.2 代码理解（最小示例）

import torch
import torch.nn.functional as F

# 假设: d_model=64, n_heads=4, d_head=16, seq_len=10
d_model, n_heads, d_head = 64, 4, 16
Wq = torch.randn(d_model, n_heads * d_head)
Wk = torch.randn(d_model, n_heads * d_head)
Wv = torch.randn(d_model, n_heads * d_head)

# Prefill: 处理整个 prompt
prompt = torch.randn(10, d_model)  # 10 tokens
Q = prompt @ Wq  # [10, 64]
K = prompt @ Wk  # [10, 64]
V = prompt @ Wv  # [10, 64]

# 保存 KV Cache
kv_cache_k = K.view(10, n_heads, d_head)  # [seq_len, n_heads, d_head]
kv_cache_v = V.view(10, n_heads, d_head)

# Decode: 生成一个新 token
new_token = torch.randn(1, d_model)
Q_new = new_token @ Wq  # [1, 64]
K_new = new_token @ Wk  # [1, 64]
V_new = new_token @ Wv  # [1, 64]

# 追加到 cache
kv_cache_k = torch.cat([kv_cache_k, K_new.view(1, n_heads, d_head)], dim=0)
kv_cache_v = torch.cat([kv_cache_v, V_new.view(1, n_heads, d_head)], dim=0)

# Attention: 只用当前 Q，对整个 cache
Q_h = Q_new.view(1, n_heads, d_head)        # [1, n_heads, d_head]
attn = torch.einsum('qhd,khd->qhk', Q_h, kv_cache_k)  # [1, n_heads, seq_len]
attn = F.softmax(attn / d_head**0.5, dim=-1)
output = torch.einsum('qhk,khd->qhd', attn, kv_cache_v)  # [1, n_heads, d_head]

3. KV Cache 的显存开销 —— 这是个大问题

3.1 计算公式

对于一层 Transformer 的 KV Cache：

KV Cache 大小 = 2 × seq_len × batch_size × n_layers × d_model × dtype_size
             = 2 × S × B × L × D × sizeof(dtype)
  • 2：K 和 V 各一份
  • S：序列长度
  • B：batch size
  • L：Transformer 层数
  • D：隐藏维度（d_model）
  • sizeof(dtype)：数据类型字节数（FP16 = 2, FP32 = 4）
交互KV Cache 显存计算器
拖动滑杆，直观感受每个因子对显存占用的影响（默认 LLaMA-2-7B + GQA-8）
—
KV Cache 总大小
—
每 token（全部层，K+V）
—
对比 7B FP16 权重（14 GB）
按 d_head = 128 计（LLaMA 系）；MHA 时 n_kv = n_heads，GQA-8 时 n_kv = 8，MQA 时 n_kv = 1

3.2 算一笔账

LLaMA-2-70B（80 层，d_model=8192，FP16）：

序列长度 Batch=1 Batch=32 Batch=128
512 160 MB 5 GB 20 GB
2048 640 MB 20 GB 80 GB
8192 2.5 GB 80 GB 320 GB

⚠️ 算法同学的直觉误区：你可能觉得"不就是缓存几个向量吗"。但实际上 KV Cache 是推理时显存占用的大头！长序列 + 大 batch 时，KV Cache 远超模型权重本身（140GB）。

3.3 显存分配全景

70B FP16 推理的显存需求 vs A100 80GB
模型权重 ~140 GB
KV Cache ~几十 GB
A100 80GB 容量线
模型权重（70B FP16）~140 GB —— 光权重就超了 KV Cache ~几十 GB —— 随序列/batch 增长 激活值 ~几 GB 框架开销 ~几百 MB

这里有两个不同层面的显存问题，千万别混淆：

问题 原因 解法 在哪章讲？
单卡放不下模型 权重 140GB > 80GB 量化（减权重大小）、张量并行（切到多卡） 第 3 章、第 4 章
KV Cache 占满剩余显存 长序列×大 batch 时 KV Cache 巨大 PagedAttention、KV 压缩、GQA 本章

💡 关键区分：PagedAttention 解决的是 KV Cache 的显存碎片问题（分配了但用不满的浪费），而不是让总需求变小。70B 模型的 140GB 权重不会因为 PagedAttention 就能塞进 80GB 的卡——这需要量化或并行。

4. 推理系统层面的 KV Cache 优化

以下优化不改模型结构，只改推理引擎的显存管理和调度策略，属于推理系统优化。

4.1 PagedAttention（vLLM 的核心创新）

问题：传统做法为每个请求预分配最大长度的连续 KV Cache（如 2048 tokens），但大多数请求用不了这么长 → 大量浪费（内部碎片）。

传统方式：按最大长度预分配 → 内部碎片
请求 A有效有效有效空空空空空浪费 5/8
请求 B有效有效空空空空空空浪费 6/8
请求 C有效有效有效有效有效空空空浪费 3/8

PagedAttention 的做法：借鉴操作系统的虚拟内存分页机制

  1. KV Cache 被分成固定大小的 block（如每 block 存 16 个 token 的 KV）
  2. 用 block table（页表）映射逻辑位置 → 物理 block
  3. block 不需要连续，按需分配
PagedAttention：逻辑块 → 物理块，按需分配、分散存储
物理 Block 池A0A1B0C0A2C1C2空空
A 的 block table逻辑 0→#0逻辑 1→#1逻辑 2→#4
B 的 block table逻辑 0→#2
C 的 block table逻辑 0→#3逻辑 1→#5逻辑 2→#6
物理块无需连续，用完再申请 → 几乎零浪费，显存利用率接近 100%

效果：vLLM 论文报告，相比传统连续分配，PagedAttention 将显存浪费从 60-80% 降到 <4%，同等显存下吞吐提升 2-4x。

4.1.1 补充：Batch 内 KV Cache 的对齐问题

Batched decode 时，不同请求的 KV Cache 长度不同，组成张量时必须对齐。传统做法和 PagedAttention 解决这个问题的方式完全不同：

传统做法：Left Padding

请求 A（3 tokens）PADPADk1k2k3Q
请求 B（5 tokens）k1k2k3k4k5Q
Left padding 保证当前 token（Q）都在最右侧对齐 → causal mask 统一处理，PAD 位 attention weight 设为 -inf

为什么必须是 left padding？如果是 right padding：

请求 Ak1k2k3PADPADQ 在 pos 2
请求 Bk1k2k3k4k5Q 在 pos 4
Right padding → Q 位置错开，causal mask 无法统一 → attention score 算错

PagedAttention：Block Table + 自定义 Kernel

PagedAttention 不是只改了显存管理——它必须配套自定义 CUDA kernel，否则 block table 存了也没用。

为什么？因为标准 attention kernel（cuBLAS）要求输入是 [batch, max_seq_len, d_model] 的连续密集张量，如果用标准 kernel，block table 里的 KV 还是得 padding 拼回密集张量才能算，那 block table 就只剩省预分配的好处了。

PagedAttention 的自定义 kernel 跳过了"拼张量"这一步：

标准 kernel 的流程：
  KV Cache → left padding 拼成 [batch, max_seq, d] 密集张量 → cuBLAS 矩阵乘

PagedAttention kernel 的流程：
  KV Cache 分散在各个 block 中
  → kernel 通过 block table 间接寻址，直接从 block 读 KV
  → 每个 warp 处理一个请求，按实际 seq_len 计算 attention
  → 从头到尾不存在 [batch, max_seq, d] 这个密集张量
  → 不需要 padding

具体执行（以 batch=2 为例）：
  请求A 的 block table: [block0][block1]         → seq_len=3
  请求B 的 block table: [block3][block5][block7]  → seq_len=5

  Warp 0 处理请求A：
    读 block0 → [k1,k2], 读 block1 → [k3]
    Q_A 对 [k1,k2,k3] 做 attention（实际 seq_len=3）
  Warp 1 处理请求B：
    读 block3 → [k1,k2], 读 block5 → [k3,k4], 读 block7 → [k5]
    Q_B 对 [k1,k2,k3,k4,k5] 做 attention（实际 seq_len=5）

  → 两个 warp 独立执行，不需要对齐到同一长度

⚠️ 这也是 PagedAttention 工程难度高的原因：它不只是换了个显存管理策略，还必须写一个全新的 attention kernel 来配合。只改显存管理、不改 kernel，计算时还是得 padding 回密集张量。

方案 显存管理 计算 kernel 是否需要 padding 实现复杂度
传统 batched decode 连续预分配 标准 kernel（cuBLAS） 需要 left padding 低
只改显存管理，不改 kernel Block table 标准 kernel（cuBLAS） 还是得 padding 拼回去 中
PagedAttention Block table 自定义 kernel 不需要 高

4.2 KV Cache 压缩 / 淘汰

长上下文时 KV Cache 太大，一些方法在推理时动态缩减：

方法 思路 效果
Sliding Window Attention 只保留最近 W 个 token 的 KV 显存固定，但丢失远距离信息
StreamingLLM 保留 sink tokens（前几个）+ 滑动窗口 稳定且省显存
H2O (Heavy-Hitter Oracle) 淘汰 attention score 低的 KV 保留重要 KV，质量损失小
Scissorhands 类似 H2O，基于重要性评分删减 20% KV 保留 95% 质量
KV Cache 量化 KV 存成 INT8/INT4 显存减半/减 3/4，质量损失可控

4.3 Continuous Batching（连续批处理）

4.3.1 Static Batching 的问题

请求 Agengengengengen结束已结束，但等别的
请求 Bgengengen结束空空已结束，空转
请求 Cgengengengengengen还在生成
A 和 B 完成后空占 slot，浪费算力

4.3.2 Continuous Batching（Iteration-level Scheduling）

迭代 1ABC
迭代 2ABC
迭代 3ABC
迭代 4AB 结束CB 完成，新请求 D 填入 ↓
迭代 5ADC
迭代 6A 结束DCA 完成，新请求 E 填入 ↓
每个 iteration 边界都可插入新请求、移除已完成请求 → GPU 不空转，利用率显著提升

这是 Orca 论文提出的，被 vLLM、TGI 等框架广泛采用。

4.3.3 Continuous Batching 的关键问题：Prefill 干扰 Decode

新请求插入时需要先做 Prefill，但 Prefill 是 compute-bound 的，会拖慢同一 iteration 里其他请求的 Decode：

迭代 Ndecode Adecode Bdecode C正常 decode
迭代 N+1prefill D · 512 tokdecode Adecode Bdecode C
迭代 N+2decode Adecode Bdecode Cdecode DD 加入 decode
N+1 里 prefill D 是 compute-bound，吃掉大量算力 → A/B/C 的 decode 全部被拖慢

这就引出了一个自然的想法：能不能把 Prefill 和 Decode 放到不同的 GPU 上？

请求流程：
  用户请求 → [请求队列] → Prefill 实例（compute-bound）→ KV Cache 传输 → Decode 实例（memory-bound）→ 返回

这就是 PD 分离架构（第四章 4.3 节详解）。

💡 所以 Continuous Batching 和 PD 分离不是互斥的，而是递进关系：Continuous Batching 解决了"已完成的请求浪费 slot"的问题，但引入了"prefill 干扰 decode"的新问题；PD 分离则进一步解决了这个问题。

5. 模型结构层面的 KV Cache 优化

以下优化改了模型结构本身，训练时就决定了，不能在已有模型上事后追加。

5.1 Multi-Query Attention (MQA) & Grouped-Query Attention (GQA)

标准 Multi-Head Attention：

每个 head 各有自己的 K 和 V
→ n_heads 组 K, V
→ KV Cache 大

Multi-Query Attention（MQA）：

所有 head 共享同一组 K 和 V（只有 1 组）
→ KV Cache 缩小 n_heads 倍！
→ 质量有一定损失，但推理速度大幅提升

Grouped-Query Attention（GQA）：

折中方案：n_heads 个 head 分成 n_groups 组，每组共享 K, V
→ KV Cache 缩小 (n_heads / n_groups) 倍
→ 质量损失更小
MHA · Q123456788 个 head 各自有 K,V → 8 组 KV
K / V12345678
GQA · Q123456788 个 head 分 4 组 → 4 组 KV
K / V1-23-45-67-8
MQA · Q123456788 个 head 共享 → 1 组 KV
K / V全部 head 共享

LLaMA-2 70B 用 GQA（8组），LLaMA-3 也用 GQA。

5.2 MQA 为什么比 Single Head 好？

一个自然的疑问：MQA 所有 head 共享同一组 K,V，这和 single head attention 有什么区别？为什么不直接用 single head？

关键区别：MQA 保留了多头的 Q，所以每个 head 有不同的"视角"。

Single Head:
  1 个 Q, 1 个 K, 1 个 V
  → 1 个 attention pattern
  → 表征能力 = d_head

MQA:
  n_heads 个 Q, 1 个 K, 1 个 V
  → n_heads 个不同的 attention pattern！
  → 每个 head 用不同的 Q 去"看"同一组 K,V
  → 表征能力 = n_heads × d_head（和 MHA 一样大）

类比：K,V 就像一本教科书（内容固定），不同的 Q 就像不同学科的学生（问题视角不同）：

  • 物理学生（Q₁）看这本书，关注力学部分
  • 数学学生（Q₂）看同一本书，关注公式部分
  • 历史学生（Q₃）看同一本书，关注背景部分

书（K,V）只有一本，但每个学生（Q）从中提取的信息不同。这就是 MQA 的核心洞察：注意力多样性主要来自 Q 的多样性，而非 K/V 的多样性。

方案 Q 数量 K/V 数量 KV Cache 大小 表征能力 质量损失
Single Head 1 1 最小 d_head 巨大（10%+）
MQA n_heads 1 小（1/n_heads） n_heads × d_head 小（1-3%）
GQA n_heads n_groups 中（n_groups/n_heads） n_heads × d_head 极小（<1%）
MHA n_heads n_heads 大 n_heads × d_head 基线

💡 MQA 的质量损失远小于退化为 single head，因为它保留了多头带来的表达力，只牺牲了 K/V 的多样性。GQA 进一步减少损失，是目前的主流选择。

6. 优化全景图

  • KV Cache 显存问题
    • 推理系统优化 不改模型，可事后部署
      • PagedAttention → 消除显存碎片，利用率 60%→96%
      • KV Cache 压缩/淘汰 → 裁剪不重要的 KV
      • Continuous Batching → 提升 GPU 利用率
        • 带来新问题：Prefill 干扰 Decode → PD 分离（第 4 章）
    • 模型结构优化 改模型，训练时决定
      • MQA → KV Cache 缩小 n_heads 倍，质量损失 1-3%
      • GQA → KV Cache 缩小 n_heads/n_groups 倍，质量损失 <1%
    • 根本解法 第 3、4 章
      • 量化 → 模型权重 + KV Cache 都缩小
      • 张量并行 → 模型切到多卡

思考题

  1. 为什么 prefill 阶段不太需要关心 KV Cache 的显存？
    参考答案

    两个层面：① Prefill 之前还没有 KV Cache，自然不存在显存问题；② 更重要的是，prefill 是 compute-bound，瓶颈在算力不在显存带宽，KV Cache 省不省、碎片不碎片，对 prefill 速度几乎没影响。真正的受害者是 decode——memory-bound，KV Cache 的大小直接决定每步要读多少数据。

  2. PagedAttention 和操作系统的虚拟内存分页，对应关系是什么？（页表、缺页中断、物理块...）
    参考答案
    操作系统概念 PagedAttention 对应
    虚拟地址空间 请求的逻辑 KV 位置（0, 1, 2, ...）
    物理页帧 GPU 上的物理 block
    页表 Block table
    缺页中断 新 token 超出已分配 block → 分配新 block
    换页（swap to disk） block 换出到 CPU 内存（GPU 显存不够时）
  3. GQA 中 group 数量如何影响推理速度和模型质量？为什么 MQA 没有成为主流？
    参考答案

    Group 越少 → KV Cache 越小 → 推理越快，但质量下降。MQA 没成主流除了质量损失（1-3%）外，还有一个原因：MQA 相比 GQA 的速度优势边际递减。Decode 阶段的内存访问不只是 KV Cache，还有模型权重。KV Cache 从 1/4（GQA-8组）再降到 1/32（MQA），省的只是 KV 部分，权重读取不变，整体加速没有数字看起来那么大，但质量损失却显著。

  4. 如果一个模型的 MHA 有 32 个 head，改成 GQA(8 组) 后，KV Cache 节省了多少？Decode 阶段的 memory-bound 瓶颈缓解了多少？
    参考答案

    KV Cache 变成 1/4（32→8 组，缩小 32/8=4 倍）✅。但不是"总 memory 变成 1/4"。Decode 每步读的内存 = 模型权重 + KV Cache。GQA 后模型权重读取不变（还是读 140GB），只有 KV Cache 部分变成 1/4。实际加速取决于 KV Cache 占总内存读取的比例：短序列（KV Cache 小，权重占主导）→ 加速不明显；长序列（KV Cache 大，可能超过权重）→ 加速显著。

  5. Continuous Batching 中，新请求的 prefill 为什么会干扰已有请求的 decode？PD 分离是如何解决这个问题的？
    参考答案

    新请求插入时需要先 prefill，prefill 是 compute-bound，吃掉大量算力，拖慢同一 iteration 里其他请求的 decode。PD 分离不是"提前算好 prefill"，而是解耦——让 prefill 和 decode 跑在不同的 GPU 上，各算各的，互不干扰。Decode 实例永远不会被 prefill 打断，TPOT 更稳定可预测。
