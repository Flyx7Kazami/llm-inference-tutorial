2. Autoscaling（自动伸缩）

2.1 为什么需要 Autoscaling？

LLM 推理的流量有鲜明的特点：

流量模式：
  · 日周期：白天高峰、凌晨低谷
  · 突发：热门事件 → 10x 流量突增
  · 长尾：凌晨流量可能只有白天的 1/20

不用 Autoscaling：
  · 按峰值配置 → 凌晨 GPU 闲置，成本浪费 80%+
  · 按均值配置 → 高峰时排队严重，SLO 违约

GPU 不便宜：A100 约 $2-3/小时，8×A100 节点约 $20/小时。多跑 10 台不必要的实例 = 每天浪费 $4800。

2.2 Autoscaling 的类型

2.2.1 Horizontal Pod Autoscaler（HPA，水平伸缩）

最常用：增减推理实例（Pod）数量

                请求量 ↑
                   │
            ┌──────▼──────┐
            │   HPA 控制器  │
            │              │
            │ 指标 > 阈值？ │──是──► 创建新 Pod
            │              │
            │ 指标 < 阈值？ │──是──► 缩减 Pod
            └──────────────┘

K8s HPA 核心参数：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 2          # 最少保持 2 个实例
  maxReplicas: 20         # 最多扩展到 20 个
  metrics:
  - type: Pods
    pods:
      metric:
        name: gpu_utilization   # 监控 GPU 利用率
      target:
        type: Utilization
        averageUtilization: 70  # 目标利用率 70%
  - type: Pods
    pods:
      metric:
        name: request_queue_depth  # 监控排队深度
      target:
        type: AverageValue
        averageValue: "10"         # 平均排队不超过 10
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30   # 30s 内不重复扩
      policies:
      - type: Pods
        value: 4                        # 每次最多加 4 个 Pod
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300   # 缩容要观察 5 分钟
      policies:
      - type: Percent
        value: 10                        # 每次最多缩 10%
        periodSeconds: 60

2.2.2 Vertical Pod Autoscaler（VPA，垂直伸缩）

调整单个 Pod 的资源请求（GPU 数量、内存等）。LLM 推理中较少使用，因为 GPU 数量通常由模型并行度决定，不好动态调整。

2.2.3 Cluster Autoscaler（CA，集群伸缩）

HPA 决定"要多少 Pod"，CA 决定"集群有没有足够的 Node 来放这些 Pod"。

HPA: 需要 15 个 Pod，但集群只有 10 个 Node 的容量
  → HPA 创建 Pod → Pending（没有 Node 可调度）
  → CA 检测到 Pending Pod → 向云厂商申请新 Node
  → 新 Node 就绪 → Pod 被调度 → 开始服务

关键延迟：

  • 申请新 GPU Node：2-5 分钟（云厂商启动时间）
  • 拉取模型镜像：1-3 分钟（几十 GB 的模型镜像）
  • 模型加载到 GPU：30s-2min（取决于模型大小和存储速度）

从"需要扩容"到"新实例就绪"通常需要 5-10 分钟！ 这是 LLM 推理 autoscaling 的核心挑战。

2.3 LLM Autoscaling 的特殊挑战

挑战 1：冷启动慢

传统 Web 服务冷启动: ~1s
LLM 推理冷启动:     ~5-10min（加载 70B 模型 + 预热）

→ 流量突增时，等新实例来不及

解决方案：

方案 做法 代价
预热池 (Warm Pool) 保持若干"已加载模型但未接入流量"的实例 常驻 GPU 费用
模型预加载 Node 启动时就拉取模型到本地盘 存储（每 Node 副本）
Serverless GPU 云厂商管理冷启动（如 AWS SageMaker Endpoint） 成本略高，灵活性低
量化 + 更小模型 用 AWQ INT4 → 加载快 2-4x 精度损失

挑战 2：指标选择

传统 Web 服务用 CPU/内存利用率做 HPA 指标，LLM 推理应该用什么？

❌ CPU 利用率：推理主要在 GPU 上，CPU 指标无意义
❌ 内存利用率：GPU 显存 ≠ 主机内存
⚠️ GPU 利用率：有一定参考价值，但 decode 阶段利用率本身就很低
✅ 请求队列深度 (Queue Depth)：最直接 —— 排队多 = 不够用
✅ 活跃请求数 / 最大并发数：利用率指标
✅ TTFT / TPOT：SLO 指标 —— 延迟升高 = 需要扩容
✅ KV Cache 利用率：显存维度 —— 快满了 = 放不下更多请求

推荐组合：

metrics:
  # 主指标：排队深度
  - name: request_queue_depth
    target: 5
  # 辅助指标：KV Cache 利用率（防止 OOM）
  - name: kv_cache_utilization
    target: 80%
  # SLO 指标：TPOT 不超过 50ms
  - name: tpot_p99
    target: 50ms

挑战 3：缩容的安全窗口

危险：刚缩掉一个 Pod，流量又来了 → 冷启动 5-10min → 雪崩

安全做法：
  · scaleDown.stabilizationWindowSeconds: 300-600
  · 缩容步长要小（每次最多缩 1-2 个 Pod）
  · 优先缩"最空闲"的 Pod
  · 优雅终止：等待当前请求完成，不接受新请求

2.4 预测性扩容（Predictive Autoscaling）

思路：基于历史流量模式，提前扩容，避免冷启动延迟。

常规 HPA:
  流量突增 → 队列积压 → 触发扩容 → 等 5-10min → 实例就绪
  └── 已经有用户等了很久 ──┘

预测性扩容:
  历史模式 → 预测"明天 10:00 流量会涨" → 提前 10min 扩容
  → 流量到达时实例已就绪 ✓

实现方式：

  • KEDA：K8s 的事件驱动 autoscaler，支持 cron trigger
  • 自定义控制器：用历史数据训练简单的时序预测模型
  • 混合策略：预测性扩容做基线 + HPA 做微调

2.5 优先级与抢占

当 GPU 资源不够时，不同请求/租户的优先级不同：

优先级（从高到低）：
  1. 在线推理请求 (SLO 严格)
  2. 在线推理请求 (SLO 宽松)
  3. 批量推理 (离线任务)
  4. 模型预热 / 测试

K8s 的 PriorityClass + Preemption：

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority-inference
value: 1000
preemptionPolicy: PreemptLowerPriority
globalDefault: false
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: batch-inference
value: 100
preemptionPolicy: PreemptLowerPriority
globalDefault: false

3. 负载均衡与请求路由

3.1 为什么传统 LB 不够？

传统 LB (Round-Robin):
  请求1 → Pod A (正在跑长序列，GPU 满载)
  请求2 → Pod B (空闲)
  请求3 → Pod A (继续往满载实例塞)

  → Pod A 过载，Pod B 闲置

LLM 推理需要感知实例状态的路由。

3.2 感知负载的路由策略

策略 做法 优缺点
Least Connections 路由到当前连接数最少的实例 简单有效，但不感知 GPU 状态
KV Cache Aware 路由到 KV Cache 余量最多的实例 显存维度最优，但需实例上报状态
Prefix-Aware 路由到已有相同 prefix cache 的实例 利用 prefix caching，减少重复计算
Queue-Depth Based 路由到排队最短的实例 延迟维度最优
Random + Retry 随机路由，超时重试其他实例 最简单，但效率低

推荐：KV Cache Aware + Prefix-Aware 组合

请求来了:
  1. 有没有实例已经缓存了这个 system prompt？
     → 有 → 路由过去（复用 prefix KV Cache）
  2. 没有缓存 → 哪个实例 KV Cache 余量多？
     → 路由到余量多的实例
  3. 所有实例都快满了 → 触发扩容

3.3 会话亲和性（Session Affinity）

多轮对话场景，同一用户的不同轮次应尽量路由到同一实例：

用户A 第1轮: [system_prompt + 问题1] → 实例1（缓存 system_prompt KV）
用户A 第2轮: [system_prompt + 问题2] → 实例1（复用 KV Cache！）

如果路由到实例2:
  → 实例2 没有 system_prompt 的 KV Cache
  → 要重新 prefill 整个 system_prompt → 慢 + 浪费显存

实现方式：基于 session_id 的 consistent hashing。

4. GPU 资源管理

4.1 GPU 型号选择

GPU 显存 算力(FP16) 带宽 适合场景 大致成本
A10 24GB 125 TFLOPS 600 GB/s 7B 量化模型 ~$1.5/h
L4 24GB 120 TFLOPS 300 GB/s 7B 量化，性价比之选 ~$0.8/h
A100 40GB 40GB 312 TFLOPS 1.6 TB/s 7B/13B FP16 ~$2/h
A100 80GB 80GB 312 TFLOPS 2 TB/s 70B 量化 ~$3/h
H100 80GB 80GB 990 TFLOPS 3.4 TB/s 70B+ FP8，极致性能 ~$4/h

选型原则：

  • 模型能放进单卡吗？
    • 能 → 多大 / 什么追求？
      • 7B 量化 → L4 / A10 便宜
      • 13B / 70B 量化 → A100 80GB
      • 追求极致 → H100
    • 不能 → 需要多少卡？→ 多卡 TP，确保 NVLink 互联

4.2 异构集群（Mixed GPU Types）

实际生产中往往有多种 GPU，需要智能调度：

集群:
  Node Group A: 4× H100 (推理主力，跑大模型)
  Node Group B: 8× A100 (跑中模型 / overflow)
  Node Group C: 16× L4 (跑小模型 / 低优先级任务)

调度策略:
  · 70B FP8 → H100
  · 70B AWQ INT4 → A100
  · 7B / 13B → L4
  · overflow 请求 → 自动降级到下一级 GPU

4.3 MIG (Multi-Instance GPU)

A100/H100 支持 MIG：一张卡切分成多个实例，每个实例独立执行。

A100 80GB MIG 模式:
  · 1g.10gb: 10GB 显存，1/7 算力 → 跑 7B INT4
  · 2g.20gb: 20GB 显存，2/7 算力 → 跑 7B FP16
  · 3g.40gb: 40GB 显存，3/7 算力 → 跑 13B INT4
  · 4g.40gb: 40GB 显存，4/7 算力 → 跑 13B FP16
  · 7g.80gb: 80GB 显存，全部算力 → 不切分

场景：
  小模型推理时，一张 A100 切 4 份，同时跑 4 个 7B 实例
  → GPU 利用率从 20% 提升到 80%

4.4 GPU 时间片共享（Time-Slicing）

更粗暴的方式：多个 Pod 共享一张 GPU，时间片轮转。

GPU 时间线Pod A · 10msPod B · 10msPod C · 10msABC
优点：简单，不需要 MIG 支持 ｜ 缺点：上下文切换开销、隔离性差、性能波动大 → 适合低优先级/开发测试，不适合生产在线推理

4.5 显存虚拟化（Unified Memory / CUDA UM）

传统方式：
  模型必须完全装入 GPU 显存，放不下就报 OOM

显存虚拟化：
  GPU 显存 + 主机内存组成统一地址空间
  频繁访问的权重留在 GPU，冷数据换出到 CPU 内存
  需要时再换入

优点：可以在小显存 GPU 上跑大模型
缺点：换入换出延迟高，decode 性能下降明显

适合：低流量 / 大模型 / 显存不足的场景
实现：llama.cpp 的 CPU+GPU 混合推理

5. CPU 推理与混合部署

5.1 什么时候用 CPU？

适合 CPU 的场景：
  · 小模型（7B 以下）+ 量化（INT4/INT8）
  · 低流量、延迟不敏感
  · 离线批量推理
  · 开发测试环境
  · 没有 GPU 的边缘节点

不适合 CPU 的场景：
  · 在线实时推理（延迟要求 < 200ms）
  · 大模型（70B+）
  · 高吞吐需求

5.2 CPU 推理框架

框架 特点
llama.cpp C++ 实现，支持 AVX2/AVX-512/NEON，量化支持好
GGML/GGUF llama.cpp 的模型格式，CPU 优化成熟
Intel BigDL-LLM Intel CPU 专用优化（AMX 指令集）
ONNX Runtime 通用 CPU 推理，支持量化

5.3 CPU + GPU 混合推理

方案 1: CPU Offloading（部分层放 CPU）
  GPU: Layer 0-19（热层，频繁访问）
  CPU: Layer 20-39（冷层，偶尔访问）

  → 适合单卡放不下的模型
  → 性能取决于 CPU↔GPU 传输带宽 (PCIe 4.0: ~64 GB/s)

方案 2: Prefill on CPU, Decode on GPU
  CPU: 处理长 prompt 的 prefill（compute-bound，CPU 多核可以胜任）
  GPU: 做 decode（memory-bound，GPU 带宽优势）

  → 适合 CPU 核心多的服务器
  → KV Cache 需要从 CPU 传到 GPU

方案 3: CPU 做后备
  GPU 实例正常服务
  流量溢出时，CPU 实例兜底（延迟高但不拒绝请求）

  → 适合应对突发流量，避免冷启动

6. 成本优化

6.1 成本构成

LLM 推理服务月成本（示例，70B 模型，8×A100 集群）：

  GPU 实例:     $40,000  (80%)  ← 大头
  网络 (InfiniBand/VPC): $3,000  (6%)
  存储 (模型/日志):  $2,000  (4%)
  运维人力:      $5,000  (10%)
  ──────────────────────
  总计:          ~$50,000/月

6.2 省钱策略

策略 1：Spot/Preemptible 实例

On-Demand A100:  ~$3/h
Spot A100:       ~$1/h  (省 60-70%)

风险：实例可能随时被回收

应对：
  · 推理本身是无状态的（KV Cache 可丢弃）
  · 被回收 → 请求重试到其他实例
  · 保持 50% On-Demand + 50% Spot → 成本降 30-35%
  · Spot 被回收时，On-Demand 实例兜底

策略 2：量化降配

70B FP16: 4×A100  → $12/h
70B AWQ:  2×A100  → $6/h   (省 50%)
70B AWQ:  1×A100  → $3/h   (省 75%)

精度损失可控（AWQ INT4 在大部分 benchmark 上损失 < 1%）

策略 3：分层部署

热路径：H100 实例（少，快）→ SLO 敏感请求
温路径：A100 实例（中等） → 普通请求
冷路径：L4 实例（多，便宜）→ 批量/低优先级

策略 4：请求调度优化

不加区分：
  所有请求 → 大模型实例 → 贵

智能路由：
  简单请求 → 小模型 (7B)  → 便宜
  复杂请求 → 大模型 (70B) → 贵但准确

  · 路由分类器判断请求复杂度
  · 80% 的请求走小模型 → 整体成本降 60%

  这就是 Cascade Inference / RouteLLM 的思路

策略 5：批处理窗口

实时推理：每个请求立即处理 → GPU 利用率低
微批处理：积累 50ms 的请求一起处理 → 利用率 ↑

  等待窗口: 0ms   → 吞吐 500 tok/s, 延迟 20ms
  等待窗口: 50ms  → 吞吐 2000 tok/s, 延迟 40ms
  等待窗口: 200ms → 吞吐 5000 tok/s, 延迟 180ms

  → 在延迟 SLO 允许的范围内，适当积累 batch → 省钱

7. 可观测性

7.1 关键监控指标

基础设施层:
  · GPU 利用率 (DCGM)
  · GPU 显存使用率
  · GPU 温度 / 功耗
  · PCIe/NVLink 带宽利用率
  · 节点 CPU / 内存 / 网络

推理层:
  · TTFT (P50/P95/P99)
  · TPOT (P50/P95/P99)
  · 吞吐 (tokens/s, requests/s)
  · 批大小 (batch_size)
  · KV Cache 利用率
  · 队列深度
  · 请求成功率 / 超时率

业务层:
  · 每日活跃用户
  · 平均请求长度 (input/output)
  · 每千 token 成本
  · SLO 达标率

7.2 告警策略

alerts:
  - name: HighTPOT
    condition: tpot_p99 > 100ms for 2min
    action: 自动扩容 + 通知

  - name: KVCacheNearFull
    condition: kv_cache_util > 90% for 1min
    action: 停止接受新请求 + 扩容

  - name: GPUMemoryOOM
    condition: gpu_memory_error_count > 0
    action: 重启实例 + 通知

  - name: HighQueueDepth
    condition: queue_depth > 50 for 3min
    action: 扩容 + 降低 batch_size

  - name: SpotReclaim
    condition: node_termination_signal
    action: 驱逐请求 + 启动替代实例

7.3 分布式追踪

一个请求从用户发出到收到完整响应，可能经过：

Client → CDN → LB → Gateway → Router → Instance →
  Tokenizer → Scheduler → Prefill → Decode×N →
  Detokenizer → Stream → Gateway → LB → CDN → Client

用 OpenTelemetry / Jaeger 追踪每个环节的耗时，快速定位瓶颈。

思考题

  1. 为什么 LLM 推理的 autoscaling 比传统 Web 服务难得多？冷启动问题有哪些解法？
    参考答案

    难在三点：

    ① 冷启动慢 2-3 个数量级：Web 服务秒级就绪，LLM 实例要申请 GPU 节点（2-5min）+ 拉取上百 GB 权重 + 加载预热（合计 5-10min），反应式扩容必然追不上流量突增。

    ② 指标不直观：CPU/内存利用率失效，GPU 利用率在 decode 阶段天然很低（memory-bound，百分之几也正常），要用队列深度、KV Cache 利用率、TTFT/TPOT 这类业务指标。

    ③ 缩容危险：刚缩掉实例流量就回来 = 5-10min 雪崩，需要长稳定窗口 + 小步长 + 优雅退出。

    冷启动解法：预热池（常备已加载模型、未接流量的 standby 实例，代价是常驻 GPU 费用）、节点预置模型（镜像/本地盘预拉权重，省下载时间）、量化（INT4 加载快 2-4 倍）、预测式扩容（用历史流量模式提前扩，让冷启动发生在流量到来之前，如 KEDA cron trigger 或时序预测）。

  2. 如果你有 10 台 8×A100 的服务器，既要服务 70B 模型又要服务 7B 模型，怎么分配？
    参考答案

    先定量化策略：70B 用 AWQ INT4（≈35GB，TP=2 一个实例）；7B FP16 单卡即可。

    分配示例：70B 是重资产，给 6 台 → 每台 4 个 TP=2 实例，共 24 实例；7B 给 3 台 → 每台 8 个单卡实例，共 24 实例；留 1 台做预热池 / 灰度 / 突发兜底。

    几个原则：① 别让两种模型抢同一组 GPU——7B 实例白占 80GB 大显存卡是浪费，按机型/卡粒度隔离，调度器打 label；② 70B 池在长 prompt 场景下按 PD 分离组织更划算，7B 混部即可；③ 两个池的 HPA 指标、预热池独立配置；④ 机动那台平时可跑 Spot 批任务（离线评测等），流量高峰时征用。

  3. Spot 实例省 60% 成本，但可能随时被回收。设计一个兼顾成本和可用性的混合策略。
    参考答案

    核心思路：On-Demand 保基线 SLO，Spot 吃弹性增量。

    ① 分层容量：常备 ~50%（对齐 p50 流量）On-Demand 实例兜底，Spot 全部被回收时服务降质不降级（排队变长，但不断流）；Spot 提供另外 50% 容量，成本直降 30-35%。

    ② 回收应对：监听 reclaim 预警（云厂商提前 30s-2min 通知）→ 立即停止派新请求 + 优雅排空在途请求 + 触发 On-Demand 池扩容；K8s 上配 PodDisruptionBudget 限制并发回收比例。

    ③ 异构对冲：Spot 跨可用区、跨机型混布（A100 Spot 没了还有 H100 Spot），单点回收不致命。

    ④ 无状态化：实例不保存不可重建的状态（KV Cache 可重算，会话亲和只做性能优化、不做正确性依赖），回收 = 损失一点预热带宽，不损失正确性。

    ⑤ 回切：Spot 池恢复后 HPA 自动把流量切回，On-Demand 缩回基线。

  4. 多轮对话场景，为什么需要会话亲和性？如果不用，最坏情况会怎样？
    参考答案

    原因：多轮对话第 N 轮的 prompt = 前 N-1 轮全部历史 + 新输入。路由到处理过前几轮的实例，历史部分 KV Cache 直接命中（prefix caching），只需 prefill 新增的一小段；路由到别的实例，整段对话历史要从头 prefill。

    最坏情况：长对话 + 高频轮次场景下雪崩。比如 20 轮对话、累计 10k tokens 历史，每轮随机路由 → 每轮全量 prefill 10k tokens，TTFT 从"几乎为 0"恶化到秒级。更要命的是 prefill 是 compute-bound，大量重复 prefill 吃光集群算力，干扰所有请求的 decode（第 4 章 prefill 干扰 decode 的场景），p99 全面恶化。相当于把每轮 O(新增长度) 的成本放大成 O(对话总长度)，算力和延迟双重付费。

    实现就是基于 session_id 的 consistent hashing。注意它是性能优化而非正确性依赖：实例挂了换一台只是重新 prefill，不丢数据。
