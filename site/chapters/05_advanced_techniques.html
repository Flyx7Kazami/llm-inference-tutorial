第五章：进阶优化技术 —— 还有哪些黑科技？

1. Speculative Decoding（投机解码）

1.1 问题：Decode 的串行性

Decode 每步只生成一个 token，且下一步必须依赖上一步的结果（自回归）。即使 GPU 算力有富余，也无法并行生成多个 token。

1.2 核心思想：猜 + 验证

用一个小模型（draft model）快速"猜" k 个 token
用大模型（target model）一次性验证这 k 个 token
接受的保留，拒绝的从拒绝点重新生成

时间线：
  传统: [t1] → [t2] → [t3] → [t4] → [t5]    5步
  投机: [draft: t1,t2,t3,t4] → [verify all]    1步draft + 1步verify
                                          如果全对 → 5步变2步！

1.3 为什么能加速？

关键洞察：大模型验证 k 个 token 只需要一次前向传播（prefill 形式），而串行生成 k 个 token 需要 k 次前向传播。

验证过程：
  把猜的 k 个 token 拼到序列后面
  一次前向传播得到每个位置的 logits
  对比每个位置的预测与 draft 的猜测
  从第 1 个不匹配的位置截断

1.4 加速比分析

假设 draft 模型的接受率为 α（每个 token 被大模型接受的概率）：

每轮投机：
  draft 生成 γ 个 token → 花费 γ × t_draft 时间
  target 验证 → 花费 1 × t_target 时间（一次前向传播）

  平均接受的 token 数 = 1 + α + α² + ... + α^(γ-1) = (1 - α^γ) / (1 - α)

加速比 ≈ (1 - α^γ) / ((1 - α) × (γ × t_draft/t_target + 1))

当 α 较高（draft 模型质量接近 target）、t_draft << t_target 时，加速比可达 2-3x。

1.5 变体

变体 Draft 来源 特点
Classic Speculative Decoding 独立小模型 最简单，但需要额外模型
Self-speculative 同一模型早退（skip layers） 不需要额外模型
Medusa 多头并行预测 不需要 draft 模型，训练额外的 prediction heads
Eagle 用特征预测而非 token 级别 更高效，接受率更高
Lookahead Decoding Jacobi 迭代并行 不需要额外模型/训练

⚠️ 算法同学的直觉误区：你可能以为投机解码"猜错了要重来，效率更低"。但实际上，即使只有 70% 的接受率，每轮平均也能产出 2-3 个 token，因为一次验证的开销远小于多次串行 decode。

2. FlashAttention

2.1 标准 Attention 的显存问题

# 标准 Attention
Q, K, V = ...  # [batch, heads, seq_len, d_head]
S = Q @ K.transpose(-2, -1)  # [batch, heads, seq_len, seq_len] ← 巨大的中间矩阵！
P = softmax(S)               # [batch, heads, seq_len, seq_len] ← 又一份大矩阵
O = P @ V                    # [batch, heads, seq_len, d_head]

问题：

  1. 显存：S 和 P 的大小为 O(N²)，序列长度 8192 时，每个 head 就占 256MB（FP16）
  2. 读写：S 写到 HBM → 读出来做 softmax → 写回 HBM → 再读出来做 @V，大量 HBM 读写

2.2 FlashAttention 的核心：Tiling + Online Softmax

关键洞察：我们不需要完整的 S 矩阵，只需要最终的 O。能不能不把 S 存到 HBM？

FlashAttention 的做法：
  1. 把 Q, K, V 分成小块（tiles），放入 SRAM（高速缓存）
  2. 在 SRAM 中计算局部 attention
  3. 用 online softmax 技巧逐步合并结果
  4. 只把最终的 O 写回 HBM

  → 不需要存储完整的 N×N attention 矩阵
  → 显存从 O(N²) 降到 O(N)
  → HBM 访问次数大幅减少 → 速度提升

Online Softmax：分块计算 softmax 的关键

标准 softmax: softmax(x) = exp(x - max(x)) / sum(exp(x - max(x)))

分块计算:
  块1: 局部 max₁, 局部 sum₁
  块2: 局部 max₂, 局部 sum₂

  全局 max = max(max₁, max₂)
  全局 sum = 校正后的 sum₁ + 校正后的 sum₂

  每处理一个新块，用校正因子更新之前的累积结果

2.3 FlashAttention 的版本演进

版本 改进 加速效果
FlashAttention-1 基础 tiling + online softmax 2-4x
FlashAttention-2 更好的 work partitioning，减少 non-matmul FLOPs 比 FA1 快 2x
FlashAttention-3 利用 H100 的异步 + FP8 + TF32 比 FA2 快 1.5-2x

2.4 对推理的影响

  • Prefill 阶段：加速明显（长序列时 2-4x），因为 prefill 是 compute-bound，FlashAttention 减少了大量冗余的 HBM 访问
  • Decode 阶段：加速有限，因为 decode 每次只处理 1 个 token，attention 矩阵很小。FlashAttention 主要减少的是 KV cache 的读取次数（Flash-Decoding）

💡 算法同学注意：FlashAttention 不改变数学结果（数值上等价于标准 attention，精度差异可忽略），纯粹是工程优化。你可以放心使用，不影响模型行为。

3. Kernel Fusion（算子融合）

3.1 问题：小算子的开销

一个 Transformer 层包含大量小算子：

LayerNorm→QKV Proj→Bias Add→Rotary→Attention→O Proj→Residual→LayerNorm→Gate/Up Proj→Activation→Down Proj→Bias Add→Residual
一个 Transformer 层里的小算子链——每个箭头都是一次潜在的 kernel 边界

每个算子都需要：读输入 → 计算 → 写输出。如果分开执行，每次都要从 HBM 读、写 HBM。

未融合HBM→LayerNorm→HBM→QKV Proj→HBM→Bias→HBM→…
每个算子之间都有一次 HBM 读写
融合后HBM→LayerNorm + QKV Proj + Bias + Rotary→HBM
一次读取、一次写回，中间结果留在 SRAM / 寄存器

3.2 常见融合模式

融合模式 融合的算子 省掉的开销
QKV Bias + Rotary bias add + RoPE 2次 HBM 读写
LayerNorm + Residual LN + add 1次 HBM 读写
Activation + Bias + Residual SiLU + bias + add 2次 HBM 读写
Attention 融合 QK^T + softmax + dropout + AV 2-3次 HBM 读写
全层融合 整个 Transformer 层 大量 HBM 读写

3.3 实现方式

  1. CUDA 手写 Kernel：性能最好，但开发成本高
  2. Triton：OpenAI 的 DSL，比 CUDA 更高层，FlashAttention 就有 Triton 实现
  3. torch.compile：PyTorch 的 JIT 编译器，自动融合算子
  4. TensorRT / cuBLASLt：NVIDIA 提供的融合算子库

⚠️ 生产级推理引擎（vLLM、TensorRT-LLM）大量使用手写 CUDA/Triton kernel 来融合算子，这是它们比纯 PyTorch 快的重要原因之一。

4. Prefix Caching

4.1 场景

很多请求有相同的 system prompt（如"你是一个有用的助手..."），重复计算这些 token 的 KV Cache 是浪费。

4.2 做法

1. 首次遇到某个 prompt prefix → 正常计算，将 KV Cache 存入缓存
2. 后续请求有相同 prefix → 直接复用缓存的 KV Cache，跳过 prefill

请求1: [system_prompt | 用户问题1] → 计算完整 KV，缓存 system_prompt 部分
请求2: [system_prompt | 用户问题2] → 复用 system_prompt 的 KV，只 prefill 用户问题2

vLLM 的 Automatic Prefix Caching (APC) 就是这个思路，利用 PagedAttention 的 block 粒度做引用计数，多请求共享同一个 prefix block。

4.3 RadixAttention（SGLang 的方法）

用 Radix Tree 管理前缀缓存，支持更灵活的复用：

  • Radix Tree（root）
    • "你是一个" → KV block 0-1
      • "有用的助手" → KV block 2-3 ← system_prompt_v1
      • "代码专家" → KV block 4-5 ← system_prompt_v2
    • "Translate" → KV block 6-7 ← 常见任务
新请求沿树匹配最长公共前缀 → 直接复用对应 KV blocks，共享前缀的部分零 prefill

技术 一句话说明 适用场景

思考题

  1. Speculative Decoding 的加速比取决于什么？如果 draft 模型特别小（接受率 50%），还有加速效果吗？
    参考答案

    三个变量：接受率 α、每轮投机 token 数 γ、draft/target 单步耗时比 c = t_draft/t_target。本章公式：加速比 ≈ (1-α^γ) / ((1-α)·(γ·c + 1))。

    α=50% 仍然有效，只要 draft 足够便宜。γ=5 时每轮期望产出 (1-0.5⁵)/(1-0.5) ≈ 1.94 个 token；若 draft 耗时是 target 的 1/50（c=0.02），一轮成本 = 5×0.02+1 = 1.1 倍单步 decode → 加速 ≈ 1.94/1.1 ≈ 1.76×。

    直觉：加速比的敌人不是低接受率，而是贵 draft。接受率低只是每轮平均产出少（但仍 >1）；draft 慢则每轮成本直接膨胀，c→1 时加速比必然 <1。所以工程上选 draft 的第一标准是小而快（比 target 小 1-2 个数量级），其次才是猜得准。

  2. FlashAttention 为什么对 decode 阶段加速有限？decode 阶段应该怎么优化 attention？
    参考答案

    FlashAttention 优化的是 attention 计算过程的访存模式：通过 tiling + 在线 softmax，避免把 N×N 注意力矩阵物化到 HBM，把 O(N²) 的 HBM 读写降到 O(N)。这是 prefill 的痛点（Q 有 N 行）。

    Decode 时 q_len=1：注意力矩阵只有 1×N，本来就没有 N² 物化问题。此时瓶颈是"从 HBM 读全部历史 K/V"（KV Cache 读取），FlashAttention 并不减少这部分——K/V 每个字节都必须读。

    Decode 阶段的 attention 优化方向是减少 KV 读取量和提高并行度：① GQA/MQA 直接砍掉 K/V 的 head 数（第 2 章）；② KV Cache 量化（INT8/FP8 KV，读取字节数减半）；③ Flash-Decoding：把 KV 序列切给不同 SM 并行处理再归并，解决小 batch 时 SM 利用不足的问题（提并行度，不减读取量）。

  3. Kernel Fusion 的本质是减少了什么开销？为什么 PyTorch eager mode 做不到？
    参考答案

    减少两类开销，第二类是大头：

    ① Kernel launch 开销：每个 CUDA kernel 启动有 ~5-10μs 的 CPU 调度成本，小 batch decode 一步要启动几十上百个 kernel，launch 间隙 GPU 空转。

    ② 中间结果的 HBM 往返：独立 kernel 的每个算子把输出写回 HBM、下一个算子再读回来；融合后中间结果留在寄存器/SRAM 里。对 memory-bound 的 decode，每一次 HBM 往返都是实打实的延迟。

    PyTorch eager mode 做不到，因为它逐算子派发执行：Python 解释一行、调一个预编译 kernel，执行时拿不到完整计算图，无从知道哪几个算子可以合并。融合需要全局视图：torch.compile（Inductor）、TensorRT、XLA 这类编译器先捕获整图，再生成融合 kernel。CUDA Graph 解决的是第①类（把整段 kernel 序列录下来一次回放），两者互补。
