第一章：LLM 推理基础 —— 推理到底慢在哪？

1. 自回归生成：LLM 推理的本质

LLM 推理是 自回归（autoregressive） 过程：每次只生成一个 token，把生成的 token 拼回输入，再生成下一个。

输入: "今天天气"
Step 1: "今天天气" → "真"     # 预测第 1 个新 token
Step 2: "今天天气真" → "好"   # 预测第 2 个新 token
Step 3: "今天天气真好" → "！"  # 预测第 3 个新 token
...

这就是推理慢的根本原因：生成 N 个 token 需要 N 次前向传播。

⚠️ 算法同学容易混淆的直觉：你可能觉得 Transformer 的并行性很好，训练时确实如此——所有 token 同时算。但推理时每次只产出一个 token，训练时的并行优势荡然无存。

2. 两个阶段：Prefill vs Decode

这是理解所有推理优化的基础中的基础。

2.1 Prefill 阶段（预填充）

  • 做什么：处理用户的完整 prompt（如 "今天天气" ），计算所有 token 的表示
  • 特点：计算量大（一次处理多个 token），compute-bound
  • 类比：读题——一次性读完所有已知信息

2.2 Decode 阶段（逐 token 生成）

  • 做什么：每次只生成一个新 token
  • 特点：计算量小（一个 token），但要读取整个模型的权重和 KV cache，memory-bound
  • 类比：答题——每次只写一个字，但每次都要翻看之前读过的内容
Prefill compute-bound
prompt 的全部 token 一次并行算完
今天天气…真
整段输入 → 一次前向 → 第 1 个新 token
→
Decode memory-bound
每次只算 1 个新 token，重复 N 次
真→好→!→…
每步都要重读全部权重 + KV Cache

2.3 关键差异对比

维度 Prefill Decode
每步处理 token 数 整个 prompt（可数百~数千） 1 个
瓶颈 算力（compute-bound） 显存带宽（memory-bound）
GPU 利用率 高（大量矩阵乘法可并行） 极低（小矩阵乘法，大部分时间在等内存读取）
优化方向 算子融合、FlashAttention 减少 memory 访问、增大 batch

💡 核心洞察：Decode 阶段，GPU 绝大部分时间在等数据从显存搬到计算单元，而不是在算。想象一个厨师（GPU）切一个土豆，大部分时间在等食材送来（memory bandwidth），而不是在切（compute）。

3. 为什么推理是 Memory-Bound？

3.1 算术强度（Arithmetic Intensity）

算术强度 = FLOPs / 内存访问字节数

它衡量的是"每从显存读 1 字节数据，能做多少次浮点运算"。这个值越大，说明计算越密集；越小，说明大部分时间在等数据搬运。

GPU 有两个性能上限：

  • 峰值算力：312 TFLOPS（A100 FP16）——每秒最多做 312 万亿次浮点运算
  • 峰值带宽：2 TB/s（A100 HBM）——每秒最多从显存读 2TB 数据

平衡点 = 算力 / 带宽 = 312 / 2 = 156 FLOP/byte

  • 算术强度 > 156 → 算力先到瓶颈 → compute-bound
  • 算术强度 < 156 → 带宽先到瓶颈 → memory-bound

补充："显存带宽"到底指什么？GPU 的内存层次结构

一个常见误解："权重已经在显存（HBM）里了，为什么还要读？"这涉及 GPU 的存储层次：

寄存器
~1 cycle · 每 SM 256KB
Tensor Core 直接读
→
L1 / 共享内存
~5 cycles · 每 SM ~100KB
tiling 的工作台
→
L2 缓存
~50 cycles · 40~80MB
→
显存 HBM
~500 cycles · 80GB (A100)
权重在这，但算不了
越往下越慢、越大。Tensor Core 不能直接访问 HBM——矩阵乘必须分块（tiling）逐块搬运上来算

关键事实：Tensor Core 不能直接对 HBM 里的数据做计算。矩阵乘法是分块（tiling）执行的——每次算一个小块（如 128×128），必须先把对应的权重块从 HBM 搬到 SM 的共享内存（SRAM），再搬到寄存器，Tensor Core 才能开始算。算完扔掉，再搬下一块。

所以"显存带宽"（A100 的 2039 GB/s）指的是 HBM → L2 → SRAM 这条路径的搬运速度，不是系统内存（DDR）→ 显存的速度（那是 PCIe，仅 ~32 GB/s）。权重推理时已经在 HBM 里，但每次矩阵乘都要从 HBM 搬到计算单元旁，搬运时间就是瓶颈。

打个比方：HBM 是仓库（放了 140GB 权重），SRAM 是工作台（~100KB），Tensor Core 是工人。工人加工一块材料很快，但材料得从仓库运过来——仓库到工作台的走廊（HBM带宽）只有 2 TB/s，工人大部分时间在等货。量化就是把材料压缩打包，同样的带宽每次能搬 2~4 倍的有效权重。

为什么不能把权重放到 SRAM 里"不读"？ SRAM 太小了——A100 有 108 个 SM，所有 SRAM 加起来不到 20MB，而 7B 模型 FP16 就有 14GB。根本塞不下，只能"用一块搬一块"。

3.2 Decode 阶段的算术强度：一层完整计算

以 LLaMA-2-7B（d=4096, d_intermediate=11008≈8d/3, 32 层）为例，batch=1 时一层做的事：

1. QKV 投影:    [1, d] @ [d, 3d]   → FLOPs: 6d²,   读: 6d² 参数
2. O 投影:      [1, d] @ [d, d]     → FLOPs: 2d²,   读: 2d² 参数
3. Attention:   Q @ K^T + attn @ V  → FLOPs: 4nd,    读: 4nd KV cache
4. Gate 投影:   [1, d] @ [d, 8d/3]  → FLOPs: 16d²/3, 读: 16d²/3 参数
5. Up 投影:     [1, d] @ [d, 8d/3]  → FLOPs: 16d²/3, 读: 16d²/3 参数
6. Down 投影:   [1, 8d/3] @ [8d/3, d] → FLOPs: 16d²/3, 读: 16d²/3 参数

线性投影部分（1-2, 4-6）：

FLOPs = 6d² + 2d² + 16d² = 24d²
FP16 下内存读取 = 24d² × 2 字节 = 48d² 字节

算术强度 = 24d² / 48d² = 0.5 FLOP/byte

Attention 部分（3）：

FLOPs = 4nd（n 是当前序列长度）
FP16 下内存读取 = 4nd × 2 字节 = 8nd 字节... 不对，KV Cache 每个 FP16 占 2 字节

K: n × d 个 FP16 = 2nd 字节
V: n × d 个 FP16 = 2nd 字节
加上 Q 和输出: ≈ 4nd 字节

算术强度 = 4nd / 4nd = 1 FLOP/byte

关键发现：所有部分的算术强度都在 0.5~1 FLOP/byte，远低于平衡点 156。

这不是巧合。对于 batch=1 的矩阵-向量乘法 y = x @ W：

FLOPs = 2 × (W 的参数量)
FP16 内存读取 = 2 × (W 的参数量) 字节

→ 算术强度 = 2 / 2 = 1 FLOP/byte（恒等于 1）

无论 W 多大、是什么形状，只要 batch=1，算术强度恒等于 ~1。

3.3 用数字感受差距

以 LLaMA-2-70B 为例（FP16，约 140GB 参数）：

阶段 每步 FLOPs 每步内存读取 算术强度 GPU 利用率
Prefill (prompt=512) ~19T ~140GB ~136 中等
Decode (batch=1) ~0.14T ~140GB ~1 ~0.64%

Decode 时每个 token 都要读一遍 140GB 的权重，但只做 0.14T 的计算。 这就是 memory-bound。

GPU 利用率的估算：

利用率 ≈ 算术强度 / 平衡点 = 1 / 156 ≈ 0.64%

→ 99% 的算力在空转等数据！

实际中会略高一点（1-3%，因为流水线重叠和 cache 命中），但量级是对的。

3.4 增大 batch 为什么能改变局面？

batch=1 时是矩阵-向量乘法 [1, d] @ [d, d]，算术强度 = 1。 batch=b 时变成矩阵-矩阵乘法 [b, d] @ [d, d]：

FLOPs = 2bd²
内存读取 = 2d² 字节（权重只读一次，多个请求共享！）

算术强度 = 2bd² / 2d² = b FLOP/byte

→ 算术强度随 batch 线性增长！
  batch=1:   算术强度 = 1    → 严重 memory-bound
  batch=32:  算术强度 = 32   → 仍然 memory-bound，但好很多
  batch=156: 算术强度 = 156  → 达到平衡点
  batch=256: 算术强度 = 256  → compute-bound
交互Roofline 探索器：batch 把工作点推过平衡点
假设 7B FP16 在 A100（312 TFLOPS · 2 TB/s）上 decode，算术强度 ≈ batch

3.5 如何缓解？

核心思路：让每次内存读取伴随更多计算

  1. 增大 batch size：多个请求共享权重读取 → 算术强度随 batch 线性提升
  2. 量化：权重从 FP16 变成 INT8/INT4 → 内存读取量减半/减四分之三
  3. Speculative Decoding：一次猜多个 token → 增加计算量

4. 推理性能的关键指标

4.1 延迟（Latency）

  • TTFT（Time To First Token）：从用户发请求到第一个 token 产出的时间
  • 主要由 Prefill 阶段决定
  • TPOT（Time Per Output Token）：每生成一个 token 需要的时间
  • 主要由 Decode 阶段决定
  • End-to-end Latency = TTFT + TPOT × 输出 token 数

4.2 TTFT 和 prompt 长度的关系

一个常见的疑问：Prefill 时所有 token 是并行计算的，为什么 TTFT 还会随 prompt 长度增长？

"并行"消除了 token 之间的串行等待，但没有消除计算量本身。n 个 token 并行过一层，FLOPs 是单 token 的 n 倍，时间也大致是 n 倍。

GPU 峰值算力固定为 312 TFLOPS（不是无限的！）

1 token 过一层:   134M FLOPs / 312T ≈ 0.43μs
512 tokens 过一层: 68.7G FLOPs / 312T ≈ 220μs

两者都跑在峰值算力，但后者 FLOPs 是前者的 512 倍 → 时间也是 512 倍。

类比：一辆车最高时速 120km/h，跑 1km 需要 30 秒，跑 512km 需要 4 小时多。不是因为车速慢，而是距离本身更远了。

另外，注意 FLOPs 和 prompt 长度不完全是线性关系——attention 部分是 O(n² × d)，而线性投影是 O(n × d²)。哪个占主导取决于 n 和 d 的关系：

n=512,  d=4096:  线性项 ≈ 8.6G, 二次项 ≈ 1.1G → 线性项 8 倍于二次项，近似线性
n=8192, d=4096:  线性项 ≈ 137G, 二次项 ≈ 275G → 二次项反超，趋向二次

→ 短序列时 TTFT 近似随 prompt 线性增长，长序列时趋向二次增长。

4.3 吞吐（Throughput）

  • Tokens/s：每秒生成的总 token 数（所有请求合计）
  • Requests/s：每秒完成的请求数

4.4 它们之间的 Trade-off

吞吐 ↑ ────────┐
               │  此消彼长
延迟 ↓ ────────┘

增大 batch → 吞吐 ↑，但单请求延迟也 ↑
减小 batch → 延迟 ↓，但吞吐也 ↓

增大 batch 导致延迟上升的原因：

  1. Attention 计算量随 batch 线性增长——每个请求都要对自己的 KV Cache 做 attention
  2. KV Cache 显存占用增加→ 可能导致显存压力 → 额外延迟

没有免费的午餐：推理优化的本质就是在延迟和吞吐之间找到合适的平衡点。

4.5 Batching 策略与 TTFT

不同的 batching 策略对 TTFT 的影响差异很大：

策略 RPM 低时 TTFT RPM 高时吞吐 适用场景
Static Batching 暴涨（等凑 batch） 好 不推荐
Continuous Batching 稳定（不等） 好 在线服务（主流）
Dynamic + Timeout 微增（< timeout） 好 折中方案
  • Static Batching：凑齐 batch_size 个请求才开始处理，低流量时等待时间暴涨
  • Continuous Batching：每个 iteration 有谁就处理谁，不等，TTFT 不受 RPM 影响
  • Dynamic + Timeout：设一个 batching window（如 50ms），窗口内到达的请求组 batch，窗口到了就处理

现代推理服务（vLLM / SGLang）普遍采用 Continuous Batching。

5. 一个完整的推理时间分解

生成 100 个 token，prompt 长度 500：

总时间 = Prefill时间 + Decode时间
       =    ~50ms    + 100 × ~20ms
       =    ~50ms    + ~2000ms
       =           ~2050ms

→ 97% 的时间花在 Decode 阶段
→ 优化 Decode 是重中之重

思考题

  1. 如果 prompt 很长（10k tokens），TTFT 会怎样？瓶颈在哪？
    参考答案

    TTFT 会随 prompt 长度上升。虽然 prefill 时 token 是并行计算的，但“并行”不等于“不花时间”——n 个 token 的 FLOPs 是单 token 的 n 倍（近似线性，长序列时趋向二次），GPU 算力固定，时间自然随 FLOPs 增长。瓶颈在算力（compute-bound）。

  2. 为什么增大 batch size 能提升吞吐但也会增大延迟？
    参考答案

    吞吐提升是因为 batch 增大 → 多个请求共享权重读取 → 算术强度从 1 提升到 b → GPU 利用率提高。延迟上升是因为：① Attention 计算量随 batch 线性增长（每个请求各做各的 attention）；② KV Cache 显存占用增加可能带来额外开销。

  3. 一个 7B 模型（FP16）在 A100（80GB）上，decode 阶段 batch=1 时的 GPU 利用率大概是多少？
    参考答案

    Decode batch=1 时算术强度 ≈ 1 FLOP/byte（FP16），A100 平衡点为 156 FLOP/byte，利用率 ≈ 1/156 ≈ 0.64%。实际中因流水线重叠等因素约 1-3%，但量级就是 1% 左右——99% 的算力在空转等数据。
