2. 主流框架对比

2.1 vLLM

定位：最流行的开源 LLM 推理引擎

核心特性：

  • PagedAttention（核心创新，KV Cache 高效管理）
  • Continuous Batching
  • 支持 TP（不含 PP）
  • 支持 GPTQ / AWQ / FP8 量化
  • Prefix Caching
  • Speculative Decoding（支持多种 draft 模型）
  • OpenAI 兼容 API

优点：

  • 社区活跃，模型支持最广
  • 开箱即用，配置简单
  • PagedAttention 效果确实好

缺点：

  • 单机为主，多机支持不如 TRT-LLM
  • 部分模型的支持有 bug（社区在快速修复）
  • 调度策略不够灵活

适合场景：大多数 LLM 推理需求，尤其是中小规模部署

# 最简启动
python -m vllm.entrypoints.openai.api_server \
  --model meta-llama/Llama-2-7b-hf \
  --tensor-parallel-size 2 \
  --quantization awq

2.2 TensorRT-LLM（NVIDIA）

定位：NVIDIA 官方的高性能推理引擎

核心特性：

  • 高度优化的 CUDA kernel（NVIDIA 手写）
  • FP8 / INT8 / INT4 量化（与 NVIDIA 硬件深度绑定）
  • TP + PP 支持
  • Inflight Batching（NVIDIA 版 continuous batching）
  • KV Cache 管理
  • TensorRT 图优化 + kernel fusion

优点：

  • 性能通常是所有框架中最高的
  • 多机多卡支持成熟
  • 与 NVIDIA 硬件（H100、L40S）配合最好

缺点：

  • 门槛高，配置复杂
  • 模型支持需要手动定义（写 Python 建模代码）
  • 编译时间长（构建 engine 需要几分钟到几十分钟）
  • 开源社区不如 vLLM 活跃

适合场景：大规模生产部署，尤其是 NVIDIA GPU 集群

2.3 SGLang

定位：高效推理 + 灵活编程的框架

核心特性：

  • RadixAttention（基于 Radix Tree 的 KV Cache 复用）
  • Continuous Batching
  • TP 支持
  • 编程模型：用 SGLang DSL 编写复杂 LLM 程序（多轮、分支、约束）
  • 与 vLLM 的 PagedAttention 不同，用 Radix Tree 管理前缀

优点：

  • 前缀复用效率极高（RadixAttention）
  • 编程模型灵活，适合复杂 LLM 应用
  • 性能在很多场景下优于 vLLM

缺点：

  • 社区规模小于 vLLM
  • 生态不如 vLLM 完善

适合场景：多轮对话、agent 场景（大量 prefix 复用）、需要编程灵活性

2.4 TGI（HuggingFace Text Generation Inference）

定位：HuggingFace 官方的推理服务

核心特性：

  • Continuous Batching
  • 量化支持（bitsandbytes / GPTQ / AWQ）
  • Watermarking
  • HuggingFace 模型无缝集成

优点：

  • 与 HuggingFace 生态无缝
  • Docker 部署方便
  • 水印等安全特性

缺点：

  • 性能不如 vLLM / TRT-LLM
  • 定制化能力弱

适合场景：快速验证、HuggingFace 生态用户

2.5 LMDeploy

定位：商汤科技的高性能推理框架

核心特性：

  • Turbomind 推理引擎（C++ 实现）
  • W4A16 量化（AWQ INT4 权重 + FP16 激活）
  • Continuous Batching
  • KV Cache 管理

优点：

  • INT4 推理性能优秀
  • C++ 实现，内存开销小

缺点：

  • 社区规模较小
  • 模型支持范围不如 vLLM

3. 框架选型决策树

  • 需要极致性能？
    • 是 → NVIDIA GPU + TensorRT-LLM
    • 否 → 需要多机多卡？
      • 是 → TensorRT-LLM 或 vLLM (TP)
      • 否 → 大量前缀复用 / Agent 场景？
        • 是 → SGLang
        • 否 → 快速上手？
          • 是 → vLLM
          • 否 → 看具体需求

4. 推理性能优化 Checklist

当你需要优化一个 LLM 推理服务时，按优先级做：

□ 1. 量化
     最简单、收益最大的优化
     AWQ INT4 或 FP8（如有 H100）

□ 2. Continuous Batching
     确保你的框架启用了 continuous batching
     vLLM / SGLang 默认开启

□ 3. KV Cache 管理
     PagedAttention (vLLM) 或 RadixAttention (SGLang)
     开启 prefix caching（如有 system prompt）

□ 4. Batch Size 调优
     增大 batch → 提升吞吐
     监控 GPU 利用率和延迟

□ 5. TP 配置
     模型放不下单卡 → TP
     确保 NVLink 互联（不要跨节点 TP）

□ 6. Speculative Decoding
     延迟敏感场景
     找一个合适的 draft 模型

□ 7. Kernel Fusion / 编译优化
     torch.compile 或换 TRT-LLM

□ 8. 分离式架构
     超大规模场景
     长短请求混合严重时

思考题

  1. 为什么 vLLM 不支持 Pipeline Parallelism？它适用于什么场景？
    参考答案

    设计取向问题。vLLM 的核心定位是"单机多卡把吞吐做高"：PagedAttention + Continuous Batching 都是单机内的优化，TP 走 NVLink 单机内互联正好匹配。PP 的价值在跨机扩展（模型大到单机放不下），但 PP 的 stage 间串行依赖会引入流水线气泡和额外调度复杂度，与 vLLM 迭代级调度（每个 iteration 自由增删请求）的设计相冲突——iteration-level 调度假设所有计算资源步调一致，PP 的流水节拍会打破这个假设。

    适用场景对照：TP 适合单机内（NVLink 带宽高，AllReduce 便宜）；PP 适合跨机（通信只有 stage 边界的 hidden state，普通 IB/以太网也扛得住）。所以 vLLM 用单机 TP 覆盖大多数部署；模型大到必须跨机时（如 405B），换 TRT-LLM 这类同时支持 TP+PP 的框架。

  2. 如果你有一个 8×A100 的服务器，要部署 70B 模型，你会怎么配置？
    参考答案

    先算账：70B FP16 权重 ≈ 140GB，单卡 A100 80GB 放不下。两条路线：

    路线 A（性能优先，卡是 80GB 版）：TP=2，每卡 70GB 权重 + KV Cache 空间，单机起 4 个实例；或 TP=4 起 2 个实例（KV Cache 更宽裕、batch 更大、吞吐更高，但 AllReduce 开销也更大）。

    路线 B（性价比优先，推荐）：AWQ/GPTQ INT4 量化 → 权重 ≈ 35GB，单卡可放，TP=1 起 8 个实例。INT4 对 70B 精度损失很小（<1%）；decode 是 memory-bound，权重读取减少 4 倍，单实例 TPOT 反而比 FP16 TP=2 更好，还省掉 AllReduce。

    实战推荐：INT4 + TP=2 起 4 实例。单实例显存 = 35GB 权重 + ~45GB KV Cache，能开大 batch；实例间独立扩缩容，挂一个还有三个兜底。框架选 vLLM：--quantization awq --tensor-parallel-size 2。

  3. 从算法工程师的角度，你觉得推理优化和算法优化（如模型结构设计）有什么可以结合的地方？
    参考答案

    开放题，几个方向：

    ① 推理感知训练/设计：量化感知训练（QAT）让模型提前适应低比特；GQA/MQA 就是"为推理改结构"最成功的案例——训练时定好，推理白拿 4-8 倍 KV Cache 缩减。

    ② 投机解码的 draft 协同设计：EAGLE / Medusa 在 target 模型上长出自投机的小头，draft 与 target 共享表征，接受率远高于独立小模型。

    ③ 稀疏性联动：MoE 的 expert 路由决定显存换入换出策略（expert offloading 按路由热度缓存）；sliding window 等 sparse attention 直接缩小 KV Cache。

    ④ 推理约束反哺算法：部署目标若是 INT4 + TP=2 + 单卡 80GB，算法侧选 d_model / n_heads / n_layers 时就该对齐硬件 sweet spot（Tensor Core 友好的维度、GQA 组数能整除 TP 度），而不是事后硬塞。

学习回顾

恭喜你完成了整个学习路线！回顾一下你学到的核心知识：

章节 核心概念 一句话总结
1. 推理基础 Prefill vs Decode 推理 97% 时间在 decode，decode 是 memory-bound
2. KV Cache PagedAttention, GQA 显存的大头是 KV Cache，分页管理消除碎片
3. 量化 GPTQ, AWQ, FP8 量化直接减少内存读取，是性价比最高的优化
4. 并行与服务 TP, PP, DP, SP/CP, EP 节点内 TP、节点间 PP、副本间 DP，长上下文叠 CP，MoE 用 EP
5. 进阶技术 Speculative Decoding, FlashAttention 用"猜+验证"突破串行瓶颈，用 tiling 减少 HBM 访问
6. 框架生态 vLLM, TRT-LLM, SGLang 选框架看场景：通用选 vLLM，极致性能选 TRT-LLM

最重要的三个直觉：

  1. LLM 推理是 memory-bound，优化围绕"减少内存访问"展开
  2. 量化、KV Cache 管理、增大 batch 是三板斧
  3. 工程优化不改算法，但能决定算法能不能用上
